# sarykov.ru — дневник Данила Сарыкова

Статический личный сайт на GitHub Pages. Основной источник записей — Telegram-канал
[@danilka2028k](https://t.me/danilka2028k), но читателю Telegram для просмотра дневника
не нужен: текст и медиа зеркалируются в этот репозиторий.

## Главное правило архитектуры

Цепочка Telegram → сайт **не должна работать как вечный процесс в GitHub Actions**.
Старый механизм с `poll_once.py`, пятиминутным long polling, самоперезапуском workflow
и передачей события из одного workflow в другой удалён. Не возвращать его.

Теперь есть два независимых пути:

1. **Основной — официальный Telegram Bot API.** Короткий stateless-запуск примерно
   раз в пять минут забирает ожидающие обновления, напрямую обновляет дневник и
   завершается.
2. **Резервный — публичная страница Telegram.** Отдельная сверка два раза в час
   проверяет `t.me/s/danilka2028k` и догоняет пропущенную запись или медиа.

Один путь не запускает другой. Они только используют одни и те же данные сайта и
общую блокировку публикации `telegram-site-publish`, поэтому две синхронизации не
толкаются одновременно.

## Telegram → сайт

### Основной путь

```text
Telegram
   │  getUpdates: message / edited_message / channel_post / edited_channel_post
   ▼
.github/workflows/telegram-gemini-bot.yml
   │
   ▼
telegram-gemini-bot/bot_api_cycle.py
   ├─ сообщения владельца → существующие обработчики bot.py / Gemini
   └─ посты канала       → data/posts.json + assets/posts/
                              │
                              ▼
                    scripts/generate-post-pages.mjs
                              │
                              ▼
                    scripts/check-site.mjs
                              │
                              ▼
                       commit + push main
                              │
                              ▼
                   явный GitHub Pages build
                              │
                              ▼
                         sarykov.ru
```

`bot_api_cycle.py` — **один цикл**, а не демон. Он:

- читает одну пачку ожидающих обновлений Telegram;
- принимает только настроенный канал;
- различает обычный пост, редактирование и медиагруппу;
- обновляет существующую запись вместо создания дубля;
- умеет собирать альбом, даже если его части пришли в разных циклах;
- скачивает доступные фото/видео через Bot API;
- приводит видео к браузерному H.264/AAC и создаёт облегчённые варианты;
- обрабатывает личные команды владельца существующими обработчиками бота;
- подтверждает Telegram offset только после успешной локальной обработки пачки.

Для прямого пути действует лимит hosted Bot API на скачивание крупных файлов.
Если конкретное медиа не удалось забрать напрямую, резервная сверка публичного канала
остаётся страховкой и может восстановить его позже.

### Резервная сверка

```text
.github/workflows/telegram-sync.yml
            │  2 раза в час
            ▼
scripts/fetch-telegram-posts.mjs
            │  публичная превью-страница канала
            ▼
data/posts.json + assets/posts/
            │
            ▼
generate-post-pages → check-site → commit → Pages
```

Это **не основной транспорт**. Парсер HTML оставлен только как независимый механизм
восстановления. Изменение разметки `t.me` не должно ломать основной Bot API-путь.

### Почему Pages запускается явно

Workflow после изменения данных сам запрашивает GitHub Pages build. Не рассчитывать
на то, что commit, сделанный `GITHUB_TOKEN`, автоматически запустит публикацию.

| `telegram-gemini-bot/bot_api_cycle.py` | основной одноразовый цикл Telegram Bot API |
| `telegram-gemini-bot/test_bot_api_cycle.py` | тесты нового транспорта и дедупликации |
| `scripts/fetch-telegram-posts.mjs` | только резервная HTML-сверка Telegram |
| `scripts/generate-post-pages.mjs` | пересобирает `dnevnik/` и `sitemap.xml` |
| `scripts/check-site.mjs` | обязательная проверка сайта перед публикацией |
| `.github/workflows/telegram-gemini-bot.yml` | основной Telegram Bot API → сайт |
| `.github/workflows/telegram-sync.yml` | резервная сверка Telegram |
| `.github/workflows/proverka.yml` | CI: сайт, JS/MJS, Python, тесты и `pip-audit` |
| `AGENTS.md` | короткие правила для следующего помощника |

Рабочая ветка — `main`.

## Устройство сайта

Публичная часть остаётся статической: backend-сервера и базы данных у читателя нет.
`index.html` намеренно содержит стили, разметку и основной клиентский JavaScript в
одном файле. Внутри него крупные разделы подписаны комментариями.

Основные панели:

- `#tab-home` — главная;
- `#tab-diary` — дневник;
- `#tab-about` — обо мне и частые вопросы;
- `#tab-contacts` — контакты.

Ключевые клиентские функции включают `showTab`, `tabByHash`, `buildTheater`,
`showInTheater`, `pickLevel`, `openTheater`, `buildEntry`, `renderInto` и
`renderFilters`.

### Плеер

Плеер собственный, без внешней библиотеки. В ленте нет `<video>`: до действия
пользователя показывается только постер, поэтому страница не начинает качать ролики
сама. Полное управление появляется в окне просмотра.

Сохранять следующие свойства:

- обычное видео и Telegram-кружочки;
- выбор качества и облегчённый уровень для медленной сети;
- перемотку мышью, пальцем и клавиатурой;
- восстановление после зависшего соединения;
- корректный `ended`/повтор;
- полный экран;
- доступный modal/focus;
- отсутствие загрузки `.mp4` до открытия ролика.

Сборщик делает уровни качества только там, где это имеет смысл; маленький исходник
вверх не растягивается.

### Медленная сеть и доступность

Не откатывать:

- локальные шрифты из `assets/fonts/` вместо внешнего CDN;
- отложенное включение шрифтов после первичной отрисовки ленты;
- `sw.js` и его версионирование `CACHE` при изменении клиентских ресурсов;
- режим `thin` для слабой сети/экономии трафика;
- `prefers-reduced-motion` и `prefers-reduced-transparency`;
- видимый `:focus-visible`;
- отсутствие видеоэлементов в карточках ленты.

### Не возвращать «антискачивание»

Глобальные запреты `contextmenu`, `dragstart`, `user-select`, `user-drag` и долгого
тапа для картинок/видео были удалены намеренно. Они не защищают опубликованный файл,
но мешают обычному UX и доступности. Не добавлять их обратно как «защиту контента».

## Что генерируется автоматически

Не редактировать вручную:

- `data/posts.json`;
- `assets/posts/`;
- `dnevnik/`;
- `sitemap.xml`;
- содержимое `assets/fonts/`, если оно пересобирается скриптом шрифтов.

Для изменения рецепта сжатия проверяйте `MEDIA_RECIPE` в
`scripts/fetch-telegram-posts.mjs`: старая и новая медиатека не должны незаметно
смешиваться.

## Проверка перед push

Минимум:

```bash
node scripts/check-site.mjs
python -m unittest discover -s telegram-gemini-bot -p 'test_*.py'
```

Для локального просмотра:

```bash
python3 -m http.server 8000
```

Проверить вручную:

- все четыре раздела и прямой `/#/dnevnik`;
- фильтры дневника;
- фото, обычное видео и кружочки;
- паузу, перемотку, качество, повтор и полный экран;
- телефон около 390 px без горизонтальной прокрутки;
- консоль без ошибок;
- отсутствие `.mp4` при первой загрузке страницы.

GitHub CI дополнительно проверяет синтаксис всех JS/MJS и Python, unit-тесты бота и
известные уязвимости Python-зависимостей.

## Публикация

```bash
git pull --rebase origin main
# правки
node scripts/check-site.mjs
git add -A
git commit -m "что сделано"
git push origin main
```

При изменении дневника автоматические workflow сами делают commit и явно запрашивают
Pages build. При обычной ручной правке сайта GitHub Pages публикует `main` по своей
настроенной схеме.

Из-за браузерного/Pages-кэша старая версия может быть видна некоторое время. Для
проверки используйте жёсткое обновление страницы, прежде чем считать правку
неработающей.

## Секреты Actions

Новый основной цикл ожидает существующие секреты репозитория:

- `TELEGRAM_BOT_TOKEN`;
- `CHANNEL_ID`;
- `ADMIN_ID`;
- `GEMINI_API_KEY` — для функций административного бота.

Модельные параметры Gemini могут задаваться repository variables. Секреты в код и
логи не писать.

---

## Запрет на возврат старой цепочки

Не создавать заново:

- `poll_once.py`;
- workflow, который держит runner несколько минут только ради long polling;
- self-dispatch / самоперезапуск workflow;
- обязательную зависимость Bot API → HTML scraper;
- схему, где зелёный workflow скрывает ошибку запуска следующего workflow.

Если основной механизм когда-нибудь меняется снова, заменять его целиком и оставлять
резервный путь независимым.
