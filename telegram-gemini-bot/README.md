# Telegram-бот: посты через Gemini

Бот превращает текст, фото, видео, кружочки (video_note) и голосовые
сообщения в готовые посты с помощью Google Gemini, а также умеет
публиковать, редактировать и удалять посты в вашем Telegram-канале.

## Вариант A: запуск через GitHub Actions (без своего сервера)

Не нужен свой компьютер или сервер — бот опрашивается прямо на серверах
GitHub по расписанию (workflow `.github/workflows/telegram-gemini-bot.yml`).

**Как это работает:** GitHub Actions не даёт держать процесс запущенным
вечно, поэтому вместо одного постоянно работающего бота workflow запускается
каждые ~5 минут и недолго (около 4 минут) опрашивает Telegram
(`poll_once.py`), обрабатывает накопившиеся сообщения и завершается.
**Из-за этого ответ бота приходит не мгновенно, а с задержкой до нескольких
минут** — это компромисс за бесплатный хостинг без своего сервера.

### Настройка

1. Открой репозиторий на GitHub → **Settings → Secrets and variables →
   Actions → New repository secret** и добавь четыре секрета:
   - `TELEGRAM_BOT_TOKEN`
   - `GEMINI_API_KEY`
   - `CHANNEL_ID`
   - `ADMIN_ID`
2. Убедись, что бот добавлен в канал администратором с правами
   публикации/редактирования/удаления сообщений.
3. Workflow уже настроен на автозапуск по расписанию (`cron: '*/5 * * * *'`).
   Можно также запустить его вручную: вкладка **Actions** → **Telegram
   Gemini bot** → **Run workflow**.
4. Логи каждого запуска смотри там же, во вкладке **Actions** — там видно,
   сколько сообщений обработано и нет ли ошибок (например, неверный ключ
   Gemini или у бота нет прав в канале).

### Важные ограничения

- **Задержка ответа** — до ~5–10 минут (реже, чем интервал cron, GitHub
  может ещё и сам откладывать запуск расписания при нагрузке).
- **Автоотключение расписания** — если в репозиторий 60 дней не было
  коммитов, GitHub сам отключает `schedule`-триггер. Тогда нужно один раз
  запустить workflow вручную (Run workflow) или сделать любой коммit —
  расписание снова заработает.
- Секреты в GitHub Actions не попадают в публичные логи (GitHub маскирует
  их значения), но всё равно не публикуй их и не коммить `.env` в репозиторий.

## Вариант B: запуск на своём компьютере/сервере

Ниже — классический способ, если хочется бота без задержек, работающего
постоянно через `bot.infinity_polling()`.

### 1. Установка

```bash
python -m venv venv
source venv/bin/activate   # Windows: venv\Scripts\activate
pip install -r requirements.txt
```

### 2. Настройка

1. Скопируйте `.env.example` в `.env`:
   ```bash
   cp .env.example .env
   ```
2. Заполните значения:
   - `TELEGRAM_BOT_TOKEN` — получите у [@BotFather](https://t.me/BotFather).
   - `GEMINI_API_KEY` — получите на https://aistudio.google.com/apikey.
   - `CHANNEL_ID` — id канала (например, `-1001234567890`) или его
     `@username`. **Бот должен быть добавлен в канал как администратор**
     с правом публикации/редактирования/удаления сообщений.
   - `ADMIN_ID` — (необязательно, но рекомендуется) ваш числовой Telegram
     id, чтобы команды `/post`, `/edit`, `/delete` работали только для вас.
     Узнать свой id можно у [@userinfobot](https://t.me/userinfobot).

### 3. Запуск

```bash
python bot.py
```

## Как пользоваться

- Отправьте боту **текст** — он вернёт красиво оформленный пост.
- Отправьте **фото или видео** — бот скачает файл, распознает содержимое
  через Gemini и предложит пост.
- Отправьте **кружочек** (video_note) или **голосовое** (voice) — бот
  расшифрует речь и превратит её в пост.
- `/post <текст>` — опубликовать текст в канал (вернёт ID сообщения).
- `/edit <ID> <новый текст>` — изменить опубликованный пост по ID.
- `/delete <ID>` — удалить пост по ID.

## Заметки

- Для видео и аудио Gemini может обрабатывать файл несколько секунд —
  бот в этот момент пишет "⏳ Обрабатываю файл...".
- Загруженные в Gemini файлы автоматически удаляются с серверов Google
  после генерации ответа.
- Скачанные из Telegram временные файлы удаляются локально сразу после
  обработки.

## История отладки и грабли (для того, кто продолжит работу над ботом)

Этот раздел — конспект всего, на что реально наткнулись при первом запуске
бота, чтобы не проходить это заново. Если бот вдруг перестанет отвечать —
начните отсюда, вероятная причина почти наверняка уже здесь описана.

### Архитектурные решения и почему

- **Бот живёт на GitHub Actions, не на сервере.** `bot.py` содержит все
  обработчики и поддерживает классический `bot.infinity_polling()` для
  локального запуска, но в проде используется `poll_once.py` — он
  импортирует обработчики из `bot.py` и опрашивает Telegram короткими
  сессиями (`POLL_SECONDS`, сейчас 240 сек), укладываясь в лимит одного
  запуска Actions. Это осознанный компромисс: бесплатно и без сервера,
  но с задержкой ответа.
- **`google-genai`, а не `google-generativeai`.** Изначально был написан
  через старый пакет `google-generativeai` (`genai.configure(api_key=...)`,
  `GenerativeModel`). Ключи Gemini, которые сейчас выдаёт AI Studio,
  начинаются на `AQ.` (не `AIzaSy`, как раньше) — старый пакет отправлял
  такой ключ так, будто это OAuth2-токен, и Google отвечал `401
  ACCESS_TOKEN_TYPE_UNSUPPORTED`. Сам ключ был рабочим (проверено через
  сырой curl с заголовком `X-goog-api-key` — тем самым, который
  генерирует AI Studio). Починилось переходом на новый унифицированный
  SDK: `from google import genai`, `genai.Client(api_key=...)`,
  `client.models.generate_content(...)`, `client.files.upload(...)`.
  Если в будущем Gemini снова откажется авторизовываться с рабочим на
  вид ключом — сначала проверяйте версию SDK, а не сам ключ.
- **`CHANNEL_ID` — числовой ID, а не `@username`.** `@username` у канала
  срабатывает, только если у канала реально есть публичный username и
  бот в нём администратор. Надёжнее — числовой ID вида `-1001234567890`.
  Способ его узнать: переслать (forward) любой пост из канала в личку
  боту — `handle_text` в `bot.py` ловит `message.forward_from_chat` и
  отвечает точным ID/username, не уходя в Gemini.
- **Бот должен быть админом канала** с правами "Публикация/Редактирование/
  Удаление сообщений", иначе `/post`, `/edit`, `/delete` падают с той же
  ошибкой `Bad Request: chat not found`, что и при неверном `CHANNEL_ID`
  — при отладке проверяйте оба варианта, ошибка одна и та же для обеих
  причин.
- **`timeout-minutes` в workflow должен быть заметно больше, чем
  `POLL_SECONDS`.** Изначально было `timeout-minutes: 5` при
  `POLL_SECONDS: 260` — впритык, и один запуск не уложился (GitHub убил
  job по таймауту, `conclusion: cancelled`, сообщение осталось
  необработанным). Сейчас `timeout-minutes: 8` / `POLL_SECONDS: 240` —
  с запасом на checkout + pip install.
- **`concurrency: cancel-in-progress: true`** — если пока идёт один
  запуск, стартует второй (например, совпали ручной запуск и
  расписание), GitHub отменяет более старый. Это ожидаемо и не баг:
  просто увидите `conclusion: cancelled` в истории запусков.
- **Расписание `*/5 * * * *` в реальности не гарантирует 5 минут.**
  Наблюдались разрывы от 2 минут до больше часа — это поведение самого
  GitHub, не что-то, что можно починить в коде. Если нужен более
  быстрый ответ прямо сейчас — вкладка **Actions → Telegram Gemini bot
  → Run workflow** запускает бота немедленно.
- **`permissions: contents: read`** у workflow — бот никогда не
  коммитит в репозиторий, только ходит во внешние API, так что права на
  запись ему не нужны (принцип минимальных привилегий).

### Где искать актуальные значения секретов

Секреты (`TELEGRAM_BOT_TOKEN`, `GEMINI_API_KEY`, `CHANNEL_ID`,
`ADMIN_ID`) заданы в **Settings → Secrets and variables → Actions** —
это единственный источник истины, GitHub не показывает их значения
после сохранения. В Google Drive (папка **Claude**) есть несколько
файлов с копиями значений, сохранённых в процессе отладки — но токен
Telegram-бота один раз перевыпускался через `/revoke` у `@BotFather`,
так что часть старых файлов там может быть устаревшей. Если бот
работает — секреты в GitHub корректны, трогать их не нужно; Drive-файлы
не обязаны быть актуальными.

### Как быстро продиагностировать проблему

1. Вкладка **Actions** репозитория → workflow **Telegram Gemini bot** →
   смотрите последние запуски и их `conclusion` (success/failure/cancelled).
2. `failure` — открыть запуск, посмотреть, на каком шаге упал, и текст
   ошибки в логе шага "Опросить Telegram и обработать сообщения".
3. `cancelled` — почти наверняка либо истёк `timeout-minutes`, либо
   совпал по времени с другим запуском (см. `concurrency` выше) — не
   всегда требует действий, часто самовосстанавливается на следующем
   запуске.
4. Бот отвечает ошибкой в самой переписке (например,
   "❌ Ошибка запроса к Gemini: ...") — текст ошибки обычно
   самодостаточен, он приходит прямо от Google/Telegram API.
