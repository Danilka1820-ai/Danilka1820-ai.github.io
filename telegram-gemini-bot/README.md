# Telegram-бот: посты через Gemini

Бот превращает текст, фото, видео, кружочки (video_note) и голосовые
сообщения в готовые посты с помощью Google Gemini, а также умеет
публиковать, редактировать и удалять посты в вашем Telegram-канале.

## Вариант A: запуск через GitHub Actions (без своего сервера)

Не нужен свой компьютер или сервер — бот опрашивается прямо на серверах
GitHub по расписанию (workflow `.github/workflows/telegram-gemini-bot.yml`).

**Как это работает:** workflow `.github/workflows/telegram-gemini-bot.yml`
примерно раз в пять минут запускает один короткий цикл
`telegram-gemini-bot/bot_api_cycle.py`. Цикл получает пачку обновлений через
Bot API, обрабатывает материалы владельца и посты канала, сохраняет результат
в репозитории, подтверждает обновления только после сохранения и завершается.
При новых или изменившихся канальных записях workflow также запрашивает
GitHub Pages build до подтверждения offset; при ошибке запроса пачка остаётся
для безопасного повтора.
Сам себя workflow не перезапускает. Резервная сверка публичного канала
запускается отдельно два раза в час.

### Настройка

1. Открой репозиторий на GitHub → **Settings → Secrets and variables →
   Actions → New repository secret** и добавь четыре секрета:
   - `TELEGRAM_BOT_TOKEN`
   - `GEMINI_API_KEY`
   - `CHANNEL_ID`
   - `ADMIN_ID`
2. Убедись, что бот добавлен в канал администратором с правами
   публикации/редактирования/удаления сообщений.
3. Основной workflow запускается по расписанию и вручную: вкладка **Actions**
   → **Telegram Bot API → сайт** → **Run workflow**. Не запускайте параллельно
   другой long polling или webhook с тем же токеном: Telegram допускает только
   одного получателя обновлений для одного бота.
4. Логи каждого запуска смотри там же, во вкладке **Actions** — там видно,
   сколько сообщений обработано и нет ли ошибок (например, неверный ключ
   Gemini или у бота нет прав в канале).

### Важные ограничения

- **Задержка ответа** — обычно до нескольких минут; GitHub может позже выдать
  бесплатный раннер.
- **Автоотключение расписания** — если в репозиторий 60 дней не было
  коммитов, GitHub сам отключает `schedule`-триггер. Тогда нужно один раз
  запустить workflow вручную (Run workflow) или сделать любой коммit —
  расписание снова заработает.
- Секреты в GitHub Actions не попадают в публичные логи (GitHub маскирует
  их значения), но всё равно не публикуй их и не коммить `.env` в репозиторий.
- Сообщения и файлы, отправленные боту, передаются Google Gemini. Не посылай секреты и
  персональные данные других людей без их согласия.
- Основной и резервный workflow используют общую concurrency-группу
  `telegram-site-publish`, чтобы не менять дневник одновременно.

## Вариант B: запуск на своём компьютере/сервере

Ниже — ручной режим через `bot.infinity_polling()`. Не запускайте его
одновременно с GitHub Actions для того же токена: оба режима получают
обновления через `getUpdates`, и Telegram может ответить конфликтом `409`.

### 1. Установка

```bash
python -m venv venv
source venv/bin/activate   # Windows: venv\Scripts\activate
pip install -r requirements.txt
```

### 2. Настройка

1. Скопируйте `.env.example` в `.env`:
   ```bash
   cp .env.example .env
   ```
2. Заполните значения:
   - `TELEGRAM_BOT_TOKEN` — получите у [@BotFather](https://t.me/BotFather).
   - `GEMINI_API_KEY` — получите на https://aistudio.google.com/apikey.
   - `CHANNEL_ID` — id канала (например, `-1001234567890`) или его
     `@username`. **Бот должен быть добавлен в канал как администратор**
     с правом публикации/редактирования/удаления сообщений.
   - `ADMIN_ID` — обязательный числовой ID вашего личного Telegram-аккаунта. Все
     команды, тексты и медиа бот принимает только от этого ID.
     Узнать свой id можно у [@userinfobot](https://t.me/userinfobot).

### 3. Запуск

```bash
python bot.py
```

## Как пользоваться

- Отправьте боту **текст** — Gemini подготовит пост, бот опубликует его
  в настроенный канал и ответит ID сообщения.
- Отправьте **фото или видео** — бот обработает вложение через Gemini,
  опубликует полученный текст в канал и сообщит результат.
- Отправьте **альбом** (несколько фото одним сообщением) — все фото уйдут в
  Gemini разом, и получится один пост, а не по одному на каждое фото.
  Основной цикл `bot_api_cycle.py` собирает части одного альбома по
  `media_group_id`, если они пришли в одной пачке Bot API. Локальный режим
  `bot.infinity_polling()` обрабатывает фото по отдельности. Альбом, который
  оказался разделён границей пачки из 100 обновлений, автоматически не
  объединяется между запусками.
- Отправьте **кружочек** (`video_note`) или **голосовое** (`voice`) — бот
  обработает речь через Gemini и опубликует полученный текст в канал.
- `/ask <вопрос>` — получить ответ Gemini **без публикации**.
- `/post <текст>` — вручную опубликовать указанный текст в канал (вернёт ID
  сообщения); команда не запускает Gemini.
- `/edit <ID> <новый текст>` — изменить опубликованный пост по ID.
- `/delete <ID>` — удалить пост по ID.

## Заметки

- Для видео и аудио Gemini может обрабатывать файл несколько секунд —
  бот в этот момент пишет "⏳ Обрабатываю файл...".
- Файлы больше 20 МБ отклоняются, а ожидание обработки Gemini ограничено 120 секундами.
- Загруженные в Gemini файлы автоматически удаляются с серверов Google
  после генерации ответа.
- Скачанные из Telegram временные файлы удаляются локально сразу после
  обработки.
- `/status` — только для владельца: показывает диагностику Gemini в текущем
  процессе. В Actions каждый цикл — новый процесс, поэтому состояние и
  история ошибок сбрасываются между запусками; это не журнал прошлых циклов.
- Автоматическая публикация запускается только для личных сообщений с ID
  отправителя `ADMIN_ID`. Чужие сообщения и сообщения канала не отправляются
  в Gemini как новый материал.
- `.github/telegram-delivery-state.json` содержит только HMAC-отпечатки ID входящих
  сообщений и статусы отправки, а не текст, Telegram ID пользователя или токен.
  В Actions попытка фиксируется отдельным commit до вызова отправки. Это
  предотвращает повторный пост при обычном повторном получении обновления.
  Если процесс аварийно завершится после checkpoint, но до отправки, статус
  будет неопределённым: бот не отправит сообщение повторно автоматически.
  Проверьте канал и при необходимости отправьте материал заново новым сообщением.

## Устойчивость к перегрузке Gemini (503/429 и сетевые сбои)

`gemini_resilience.py` — отдельный модуль с тремя независимыми слоями
защиты, подробно объяснёнными в его собственном докстринге:

1. **Повтор внутри одной модели** — включаем встроенный в `google-genai`
   SDK механизм (экспоненциальная задержка с джиттером на HTTP-уровне,
   через `client.models.generate_content` → `retry_options`), а не
   изобретаем свой цикл `time.sleep()` поверх официального. Это именно
   то, что рекомендует документация Gemini
   (https://ai.google.dev/gemini-api/docs/troubleshooting).
2. **Резервные модели** — если основная модель не ответила совсем,
   пробуем модели из `GEMINI_FALLBACK_MODELS` по порядку.
3. **Предохранитель** — после нескольких подряд отказов модель на время
   исключается из перебора, чтобы не тратить весь бюджет запроса на
   заведомо мёртвую модель. Живёт только в памяти текущего запуска
   `bot_api_cycle.py` (без бесплатной постоянной базы этого не сохранить
   между перезапусками — честно, а не притворяясь надёжным).

Настройка — переменные окружения, у всех есть рабочие значения по
умолчанию:

- `GEMINI_PRIMARY_MODEL` — основная модель (по умолчанию `gemini-flash-latest`).
- `GEMINI_FALLBACK_MODELS` — резервные модели через запятую (по умолчанию
  `gemini-flash-lite-latest` — облегчённый официальный псевдоним с отдельной
  квотой, обычно менее нагруженный, чем основной `gemini-flash-latest`).
  Если Google переименует или уберёт этот псевдоним, проверьте актуальный
  список в вашем Google AI Studio (https://ai.google.dev/gemini-api/docs/models)
  и впишите нужный через эту переменную.
- `GEMINI_REQUEST_TIMEOUT` — таймаут одного HTTP-запроса к Gemini,
  секунды (по умолчанию 30).
- `GEMINI_MAX_RETRIES` — сколько раз SDK повторит запрос к одной модели,
  включая первую попытку (по умолчанию 3).
- `GEMINI_CIRCUIT_THRESHOLD` / `GEMINI_CIRCUIT_COOLDOWN` — порог подряд
  отказов и время исключения модели предохранителем, секунды (по
  умолчанию 3 и 60).

Пользователь никогда не видит сырой `503 UNAVAILABLE` или JSON ошибки —
`gemini_resilience.friendly_error_message()` показывает понятный русский
текст, а полная причина уходит в `print()` (лог запуска Actions).
Ошибка ключа/доступа (401/403) не лечится ни повтором, ни резервом и
поднимается сразу — та же причина сломает и остальные модели.

## Архитектура и диагностика

Актуальные компоненты Telegram → сайт описаны в корневом `README.md`.
Основной цикл находится в `bot_api_cycle.py`, команды и обработчики —
в `bot.py`, резервная сверка канала — в `scripts/fetch-telegram-posts.mjs`.

### Архитектурные решения и почему

- **Основной режим — один scheduled запуск `bot_api_cycle.py`.** Workflow
  выполняется примерно раз в пять минут, получает одну пачку обновлений,
  обрабатывает её и завершается. Отдельная резервная сверка работает дважды
  в час; ни один workflow не запускает сам себя.
- **Альбом группируется в `bot_api_cycle.py`.** У Telegram каждое
  фото альбома — отдельный апдейт с общим `media_group_id`, а подпись есть
  только у одного из них. Основной цикл объединяет их по `media_group_id`,
  даже если части поступили в разных пачках. Локальный
  `bot.infinity_polling()` обрабатывает фото по отдельности.
- **`google-genai`, а не `google-generativeai`.** Изначально был написан
  через старый пакет `google-generativeai` (`genai.configure(api_key=...)`,
  `GenerativeModel`). Ключи Gemini, которые сейчас выдаёт AI Studio,
  начинаются на `AQ.` (не `AIzaSy`, как раньше) — старый пакет отправлял
  такой ключ так, будто это OAuth2-токен, и Google отвечал `401
  ACCESS_TOKEN_TYPE_UNSUPPORTED`. Сам ключ был рабочим (проверено через
  сырой curl с заголовком `X-goog-api-key` — тем самым, который
  генерирует AI Studio). Починилось переходом на новый унифицированный
  SDK: `from google import genai`, `genai.Client(api_key=...)`,
  `client.models.generate_content(...)`, `client.files.upload(...)`.
  Если в будущем Gemini снова откажется авторизовываться с рабочим на
  вид ключом — сначала проверяйте версию SDK, а не сам ключ.
- **`CHANNEL_ID` — числовой ID, а не `@username`.** `@username` у канала
  срабатывает, только если у канала реально есть публичный username и
  бот в нём администратор. Надёжнее — числовой ID вида `-1001234567890`.
  Способ его узнать: переслать (forward) любой пост из канала в личку
  боту — `handle_text` в `bot.py` ловит `message.forward_from_chat` и
  отвечает точным ID/username, не уходя в Gemini.
- **Бот должен быть админом канала** с правами "Публикация/Редактирование/
  Удаление сообщений", иначе `/post`, `/edit`, `/delete` падают с той же
  ошибкой `Bad Request: chat not found`, что и при неверном `CHANNEL_ID`
  — при отладке проверяйте оба варианта, ошибка одна и та же для обеих
  причин.
- **Запуск ограничен 15 минутами.** Это общий предел одного короткого цикла,
  включая установку зависимостей, обработку обновлений и подготовку страниц.
- **Оба workflow используют `concurrency: telegram-site-publish`.** Второй
  запуск ждёт освобождения группы и не отменяет текущий.
- **Основной график — примерно раз в пять минут; резервный — дважды в час.**
  GitHub может задержать scheduled workflow. Запуск вручную доступен на
  вкладке **Actions**.
- **Публикация меняет репозиторий.** Telegram workflow имеет права
  `contents: write` и `pages: write`, коммитит изменения данных и явно
  запрашивает GitHub Pages build после публикации.
- **Gemini иногда отвечает `503 UNAVAILABLE` («модель сейчас перегружена») —
  это временная перегрузка на стороне Google, не ошибка запроса.** Сначала
  бот показывал сырой JSON ошибки и сдавался; затем появился свой цикл
  повторов прямо в `bot.py`. Из капитального ремонта эта логика переехала
  в отдельный `gemini_resilience.py` и стала честнее: повтор внутри одной
  модели теперь делает сам SDK (официальный `retry_options`, а не наш
  `time.sleep()`), плюс появились резервные модели и предохранитель — см.
  раздел «Устойчивость к перегрузке Gemini» выше. Ошибка ключа/доступа
  (401/403) по-прежнему падает сразу, без бессмысленных повторов.
- **`threaded=False` у `telebot.TeleBot(...)`** оставляет обработчики в
  вызывающем потоке. Так `bot_api_cycle.py` может дождаться окончания
  обработки администраторских обновлений перед подтверждением пачки.

### Где искать актуальные значения секретов

Секреты (`TELEGRAM_BOT_TOKEN`, `GEMINI_API_KEY`, `CHANNEL_ID`,
`ADMIN_ID`) задаются только в **Settings → Secrets and variables → Actions**.
GitHub не показывает их значения после сохранения. Не храните копии токенов в обычных файлах;
если копия утекла, перевыпустите токен/ключ и обновите Secret.

### Как быстро продиагностировать проблему

1. Вкладка **Actions** репозитория → workflow **Telegram Gemini bot** →
   смотрите последние запуски и их `conclusion` (success/failure/cancelled).
2. `failure` — открыть запуск и посмотреть упавший шаг. В основном workflow
   это может быть получение обновлений Bot API, обработка, проверка данных,
   публикация commit или запрос Pages build.
3. `cancelled` — это больше не штатная часть цепочки. Проверьте таймаут, ручную отмену
   и логи предыдущих шагов.
4. Ошибка в переписке может относиться к Gemini или правам бота в канале.
   Для Telegram API проверьте наличие и формат `TELEGRAM_BOT_TOKEN`,
   `CHANNEL_ID`, `ADMIN_ID`, а для Gemini — `GEMINI_API_KEY` и доступность
   настроенной модели. Не публикуйте значения секретов вместе с журналом.
