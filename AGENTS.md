# Инструкция для помощника, который правит этот сайт

Прочитайте этот файл до изменений. Рабочая ветка — `main`.

## Что это

`sarykov.ru` — статический дневник Данила Сарыкова на GitHub Pages. У публичной
части нет backend-сервера и базы данных. Тексты и медиа зеркалируются из
Telegram-канала `@danilka2028k` в репозиторий, поэтому читателю Telegram для
просмотра сайта не нужен.

## Критически важно: новая Telegram-архитектура

Старая цепочка удалена. **Не восстанавливать `poll_once.py`, вечный long polling
в GitHub Actions, self-dispatch workflow или схему «workflow запускает workflow,
который парсит HTML Telegram».**

Текущая схема состоит из двух независимых путей:

1. `.github/workflows/telegram-gemini-bot.yml` →
   `telegram-gemini-bot/bot_api_cycle.py` — основной короткий stateless-цикл
   официального Telegram Bot API примерно раз в пять минут. Он обрабатывает
   сообщения владельца и напрямую пишет посты канала в данные сайта.
2. `.github/workflows/telegram-sync.yml` → `scripts/fetch-telegram-posts.mjs` —
   резервная сверка публичной страницы канала два раза в час. Это аварийное
   восстановление, а не основной транспорт.

Оба workflow используют concurrency-группу `telegram-site-publish`, чтобы не
публиковать дневник одновременно. После изменения данных workflow явно запрашивает
GitHub Pages build.

Если эту систему когда-либо придётся менять, меняйте узел целиком. Не добавляйте
самоперезапускающийся polling обратно.

## Где код

- `index.html` — весь интерфейс сайта: стили, HTML и основной клиентский JS;
- `sw.js` — кэш и offline-поведение;
- `telegram-gemini-bot/bot.py` — команды административного бота;
- `telegram-gemini-bot/bot_api_cycle.py` — основной Telegram-транспорт;
- `scripts/fetch-telegram-posts.mjs` — только резервная Telegram-сверка;
- `scripts/generate-post-pages.mjs` — страницы `dnevnik/` и `sitemap.xml`;
- `scripts/check-site.mjs` — проверка сайта;
- `README.md` — подробная карта архитектуры.

Генерируемые файлы руками не править: `data/posts.json`, `assets/posts/`,
`dnevnik/`, `sitemap.xml`.

## Перед каждым push

```sh
git pull --rebase origin main
node scripts/check-site.mjs
python -m unittest discover -s telegram-gemini-bot -p 'test_*.py'
git add -A
git commit -m "что сделано"
git push origin main
```

CI дополнительно проверяет все JS/MJS, синтаксис Python, unit-тесты и Python-зависимости.

## Чего делать нельзя

1. Не возвращать старую self-chaining Telegram-цепочку.
2. Не делать HTML-парсер Telegram единственным способом доставки постов.
3. Не тянуть внешние CDN для шрифтов или плеера: всё критичное должно лежать в
   репозитории.
4. Не заменять собственный плеер внешней библиотекой без доказанной необходимости.
5. Не возвращать `<video>` в карточки ленты: видео должно грузиться только после
   действия пользователя.
6. Не удалять `sw.js`, режим `thin`, `prefers-reduced-motion`,
   `prefers-reduced-transparency` и доступный focus.
7. Не возвращать глобальные запреты `contextmenu`, `dragstart`, `user-select`,
   `user-drag` и долгого тапа как «антискачивание». Они намеренно удалены: файл
   всё равно доступен браузеру, а UX и доступность страдают.
8. Не править вручную генерируемые данные и медиа.
9. Не считать зелёный workflow достаточным, если менялся транспорт: смотрите
   конкретные шаги и логи Bot API/публикации.

## Проверка интерфейса

После изменений сайта проверить хотя бы:

- `Главная`, `Дневник`, `Обо мне`, `Контакты`;
- прямой `/#/dnevnik`;
- фильтры;
- фото, обычное видео и кружочки;
- паузу, перемотку, качество, повтор и полный экран;
- мобильную ширину около 390 px без горизонтальной прокрутки;
- консоль без ошибок;
- отсутствие загрузки `.mp4` до открытия ролика.
